### 1.2 Расхождения

**1.2.1. Приоритет P1 отчёта — не тот дефект, который важнее всего.**

Отчёт поставил на первое место расхождение между `--no-sandbox` и `--executor-user`.
Это дефект **конфигурации**: он требует, чтобы оператор сам отключил песочницу.
Найденная ниже дыра в границе «Producer ≠ Verifier» (F-01, F-02) работает при
**полностью включённой песочнице** и в режиме по умолчанию. По критерию
«что ломает гарантию проекта, заявленную в `AGENTS.md` §2.8», F-01 существенно
серьёзнее.

**1.2.2. Отчёт не проверил двигатель вообще.**

Весь отчёт — про песочницу, ACL и эксплуатацию. Механизмы, ради которых
существует проект (независимый верификатор, fail-closed семантика журнала,
hash-цепочка), не разобраны. Именно там лежит самое тяжёлое.

**1.2.3. P1 «нет сети» — это не дефект реализации.**

Согласен с формулировкой самого отчёта: это осознанный размен (нужен доступ к
API модели). В плане это идёт как работа над моделью угроз и белым списком
окружения, а не как «баг».

### 2.1 F-01 — разбор и воспроизведение

Проект уже содержит правильный предикат — `_report_is_current()`
(`engine.py:712-746`), чей докстринг прямо говорит нужное:

> «Only the first may reach a gate: a verdict that predates the bytes it judges
> is history».

Но он подключён **только к маршрутизатору work order** (`engine.py:1006`,
`engine.py:1036`), то есть к выбору следующей задачи. Гейт — это отдельная
точка входа (`cli.py:382`, `cli.py:345`), и она `_report_is_current` не зовёт.

`gate_approve` (`engine.py:1542-1553`) и `task_accept`
(`engine.py:2104-2117`) проверяют **грамматику** отчёта (валидна ли структура,
есть ли `PASS`) и **не** проверяют **свежесть** (были ли байты, которые
вердикт описывает, теми же самыми).

Воспроизведение (задача; `/tmp/opencode/repro_stale_verdict.py`):

1. продюсер сдаёт `TASK-001` → статус `review`;
2. верификатор пишет PASS-отчёт по текущим байтам;
3. продюсер меняет `product/src/todo.py` и пересдаёт задачу
   (`submit_work`/`task_submit` это разрешают: `engine.py:1282` разрешает статус
   стадии `review`);
4. `factory task accept` — **принимает задачу по старому отчёту**.

Результат: `task status = accepted`, на диске код, который никто не
проверял.

Воспроизведение (стадия; `/tmp/opencode/repro_gate_stale.py`): `factory gate
approve --gate gate_s4` закрывает стадию по устаревшему отчёту.

**Почему это не ловится хеш-цепочкой.** Журнал остаётся согласованным:
`producer → VERIFY → GATE_DECISION`, все хеши и `seq` верны, `verify_chain`
не находит ошибок. Подмена не оставляет следов, потому что подменяется не
запись, а **смысл** записи: вердикт формально валиден и формально выдан
верификатором — но относится к другим байтам.

**Почему это не ловится песочницей.** Никак: дыра находится в логике движка и
не требует никакой неверной конфигурации. Она воспроизводится в режиме по
умолчанию при полностью включённом bwrap.

**Почему это важно именно проекту.** `AGENTS.md` §2.8: «`PASS` пишет только
`02-independent-verifier`». Формально так и есть — но вердикт, вынесенный над
чужими байтами, не выполняет обещания. `docs/audit/handoff-1.0.9.md:186`
фиксирует намерение: «гейт и верификатор получают шаг только при валидном
**и свежем** отчёте». Слово «свежем» реализовано для work order и не
реализовано для гейта.

### 2.2 F-04 — почему продюсер может написать отчёт верификатора

`_collect_writable_paths` (`loop.py:165-176`) для файлового артефакта в
подкаталоге добавляет **родительский каталог**, а не сам файл:

```python
        elif candidate.parent == (project if is_root else run):
            add(candidate, False, root=is_root)
        else:
            add(candidate.parent, True, root=is_root)   # <-- весь каталог writable
```

Спека `artifacts/spec.md` → writable становится `run/artifacts/`, а внутри
лежит `artifacts/verification/<stage>/verification.md` — отчёт верификатора.
Песочница делает writable весь корень прогона (`sandbox.py:161-164`), а
tripwire (`guard.py:16-22`) считает только 5 файлов — запись под `artifacts/`
не отслеживается вовсе.

Дополнительно: в `_stage_work_order` исключение `VERIFICATION_IDS` из
write-scope сделано **условным** (`engine.py:996-1003`): исключение срабатывает
только когда отчёт валиден. Когда отчёт отсутствует или невалиден, спека
верификатора остаётся в списке writable-артефактов продюсера.

Итог: продюсер может написать синтаксически корректный PASS-отчёт, и
`_complete_verification` (`loop.py:304-330`) прочитает его с диска.

## 3. План исправлений

Одиннадцать коммитов, каждый атомарный и проверяемый. Порядок — по убыванию
серьёзности; коммиты 1–3 закрывают дыру в границе доверия, 4–7 — границу
исполнителя, 8–11 — устойчивость и проверяемость.

### Коммит 1 — P0: гейт требует свежего вердикта (F-01)

**Файлы:** `factory/engine.py`, `tests/test_verify_task_lineage.py`

1. Вынести единый предикат свежести рядом с `_report_is_current`:

   ```python
   def _verdict_is_fresh(run_dir, *, stage_id, task_id, report_path) -> bool:
       """True when no producer submission came after the report was written."""
   ```

   Он учитывает и `ARTIFACT_SUBMIT` продюсера, и `VETO`, и отклонённый
   `GATE_DECISION` — то есть объединяет семантику `_report_is_current` и
   `verification_is_stale` (заодно снимает F-11).

2. `gate_approve` (`engine.py:1542`): после проверки грамматики отчёта
   потребовать `_verdict_is_fresh`; при `False` — `VerificationError` с
   понятным текстом («the verdict predates the last submission»).

3. `task_accept` (`engine.py:2104`): то же самое.

4. Fail-closed: если определить свежесть нельзя (отчёт не найден, журнал
   не читается) — считать вердикт несвежим и отказывать.

**Почему:** вердикт — это утверждение о конкретных байтах. Проверка грамматики
без проверки свежести — это проверка формы, а не содержания.

**Проверка:** тест-регрессия из `/tmp/opencode/repro_stale_verdict.py`,
переведённый в `tests/`: после пересдачи задачи `task_accept` обязан бросить
`VerificationError`; тот же сценарий для `gate_approve`.

### Коммит 2 — P0: `factory verify` видит устаревший вердикт (F-02)

### Коммит 6 — P1: ACL — default-ACL и права на каталог (G-7, P1 отчёта)

**Файлы:** `factory/runtime/isolation.py`, `factory/cli.py`, `tests/`

1. `grant_run_tree` (`isolation.py:206-219`): **не** ставить default ACL
   `u:<executor>:rwX` на корень прогона. Default ACL наследуется новыми
   inode’ами, и именно этим атомарная запись движка (`journal.py:257`,
   `journal.py:516`, `checkpoint.py:111`) отменяет отзыв доступа.

2. Грантовать явные пути: `artifacts/`, `tasks/`, `product/` — тем, кому
   они нужны, а не всему дереву прогона рекурсивно.

3. Снять права исполнителя с **родительских каталогов** control plane.
   Права на каталог дают `unlink`/`rename` его содержимого, поэтому отзыв
   только по inode не защищает ничего: `setfacl -x` на файле бессмысленно,
   если есть `rwx` на каталоге, где файл лежит.

4. `factory doctor`: выводить предупреждение, если на корне прогона есть
   default ACL, дающий исполнителю запись, и если у исполнителя есть `w` на
   каталоге, содержащем control plane.

**Почему:** отчёт справедливо называет `--no-sandbox` небезопасным. Но даже
без него ACL-слой сейчас не защищает то, что думает защищать: это видно по
`getfacl` на новом `state.json` — `user:<executor>:rwx #effective:rw-`.

**Проверка:** интеграционный тест (коммит 10) — создать и атомарно заменить
`state.json` после ACL-настройки, затем проверить права нового inode.

## 5. Критерии закрытия

1. Задача, пересданная после вердикта, **не** принимается: `task_accept`
   бросает `VerificationError`; гейт на устаревшем отчёте не закрывается.
2. `factory verify` на таком прогоне возвращает ошибку, а не пустой список.
3. Продюсер не может создать/изменить `artifacts/verification/**` и
   `tasks/*/verification/**` — ни через write-scope, ни через rename.
4. Symlink, подложенный исполнителем в `runtime/evidence/`, приводит к
   **ошибке**, а не к записи от имени оператора.
5. После атомарной замены `state.json` новый inode **не** даёт исполнителю
   права записи; у каталога, содержащего control plane, нет `w` для
   исполнителя.
6. `pytest -q` зелёный; новый integration-job проверяет реальную границу и
   публикует список пропущенных платформенных проверок.

## 6. Что осталось за пределами этого цикла

- **Сеть.** Сознательно оставлена ради доступа к API модели. Ограничение
  egress — отдельная задача (прокси с allowlist доменов), не чинится патчем в
  этом цикле. Пока это остаётся: агент может exfiltrate то, что прочитает.
- **Секреты в world-readable файлах.** Снижается белым списком окружения и
  исключением `~/.ssh`/`~/.aws` (коммит 10), но не решается в общем виде.
- **Доверие к модели.** Верификатор — тоже LLM. Гарантия «Producer ≠ Verifier»
  сегодня означает «разные роли и разный контекст», а не «независимую
  проверку». Это стоит написать в `docs/threat-model.md` явно.
- **Сторонние скиллы.** Карантин fail-closed закрыт; `AUD-01..AUD-12` из
  `NEXT_SESSION_PROMPT.md` — отдельный цикл.
