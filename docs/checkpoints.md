# Подписанные контрольные точки журнала

Хеш-цепочка `blackbox.jsonl` доказывает, что журнал внутренне согласован, но не
доказывает авторство: кто может писать в `runs/<id>/`, тот может пересчитать
`hash` и `prev_hash` у всех событий. `factory sign` закрывает именно этот класс
атак — подписывает голову цепочки ключом, которого в каталоге прогона нет.

## Как это работает

```text
events ──▶ голова цепочки (hash последнего события)
                  │
                  │ HMAC-SHA256(ключ, run_id|key_id|event_count|head_hash|created_at)
                  ▼
        run/<id>/checkpoint.json          копия для чтения
        <store>/<run_id>.json             якорь: ключ и store вне runs/
```

Подпись накрывает `event_count` и `head_hash`. Поэтому:

- переписанная цепочка даёт другую голову → `diverged`;
- усечение журнала до ранее подписанного состояния → `rolled_back`;
- новые события после подписи → `stale` (это нормально между гейтами).

## Команды

```bash
# ключ: 32+ байта, hex или сырые байты; файл — chmod 600 и вне runs/
head -c 32 /dev/urandom | od -An -tx1 | tr -d ' \n' > ~/.config/factory/journal.key
chmod 600 ~/.config/factory/journal.key

factory sign   --run-id demo-01 --key-file ~/.config/factory/journal.key
factory verify --run-id demo-01 --key-file ~/.config/factory/journal.key
```

`--store` задаёт каталог якоря (по умолчанию `~/.local/state/factory/checkpoints`,
переопределяется `FACTORY_CHECKPOINT_DIR`). Ключ можно передать через
`FACTORY_JOURNAL_KEY` вместо файла.

`factory verify` печатает состояние чекпоинта и добавляет ошибку, только когда
журнал действительно разошёлся с подписью. `--json` отдаёт блок `checkpoint`.

## Состояния

| Состояние | Что значит | Это ошибка `verify` |
| :--- | :--- | :--- |
| `unsigned` | чекпоинта нет | нет — прогон просто не привязан к ключу |
| `signed` | голова совпадает с последней подписью | нет |
| `stale` | после подписи появились новые события | нет — переподпишите на следующем гейте |
| `rolled_back` | голова равна **старой** подписи | да: журнал усечён |
| `diverged` | голова не совпадает ни с одной подписью | да: цепочка переписана |
| `run_copy_edited` | `checkpoint.json` в прогоне не равен копии в store | да |

## Ключ

- Минимум 32 байта: короткий ключ делает подпись декоративной.
- Файл ключа вне каталога прогона — `sign` отказывается подписывать ключом,
  который лежит внутри `runs/<id>/`: такой ключ доступен исполнителю.
- Store тоже вне прогона: `sign` проверяет это явно.
- Store не должен попадать в `--sandbox-rw`: путь, открытый на запись
  исполнителю, перестаёт быть якорем. Если ключ утёк, но store недоступен на
  запись, подделка всё равно ловится по расхождению с копией в прогоне.
- Ключ не попадает в журнал, артефакты и `--json`; наружу выходит только
  `key_id` — первые 16 hex SHA-256 от ключа.
- Потеря ключа не «ломает» прогон, но старые подписи проверить уже нельзя:
  `verify` скажет, каким `key_id` подписан чекпоинт.

## Чего это не делает

- **HMAC — симметричная подпись.** Проверяющий должен держать ключ; третья
  сторона не может проверить журнал, не получив секрет. Ed25519 дал бы
  публичную проверку — это отдельное изменение с новой зависимостью.
- **Store не append-only.** Файл якоря перезаписывается целиком при подписи;
  история подписей лежит внутри и подписана построчно, но удаление самого файла
  выглядит как `unsigned`, а не как подделка. Для сильной модели угроз копию
  `store` складывайте туда, куда исполнитель не пишет (внешний диск, git,
  append-only хранилище).
- **Права root не покрыты.** Пользователь, который может писать в `store` и
  читать ключ, подпишет что угодно.
- **Автоподписи в `factory run` нет.** Подпись ставит человек или CI на гейте;
  иначе исполнитель подписывал бы сам себя.

## Проверка

```bash
.venv/bin/python -m pytest tests/test_checkpoint.py -q
```

Тесты покрывают: чистую подпись, `stale` после новых событий, переписанную
цепочку, усечение до подписанной головы, чужой ключ, ключ и store внутри
прогона, отказ подписывать уже сломанную цепочку, правку копии в прогоне.
