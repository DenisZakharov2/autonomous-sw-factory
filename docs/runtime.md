# Runtime: как фабрика исполняет work order

Документ описывает пакет `factory/runtime/` версии `0.3.0`: контракт исполнителя,
цикл `factory run`, обогащение work order, учёт бюджета, защиту и состояние
адаптеров. Он дополняет `DESIGN.md` (концепция) и `PIPELINE.md` (стадии).

## 1. Зачем рантайм

До `0.1.2` движок умел выдавать work order, проверять артефакты и вести журнал,
но не умел их *производить*: между `factory next` и `factory submit` стоял
человек с руками. `factory/runtime/` закрывает этот разрыв: получает order,
отдаёт его исполнителю, проверяет, что на диске появились **объявленные**
артефакты, сдаёт их и закрывает только те гейты, у которых approver — роль.

Первый результат — не «автономная фабрика на 22 роли», а один честный прогон
`nano` от `s00_intake` до `s9_learn`, где артефакты пишет исполнитель, а не
скрипт.

## 2. Контракт Executor

`factory/runtime/base.py`:

```python
class Executor(Protocol):
    name: str
    def execute(self, order: dict, context: RunContext) -> ExecutionResult: ...

@dataclass
class ExecutionResult:
    exit_code: int
    stdout: str
    stderr: str
    artifacts: list[str]      # отчёт исполнителя, НЕ список для submit
    summary: str
    usage: dict               # tokens_total, usd, seconds (любое может быть None)
    transcript_path: str | None

@dataclass
class RunContext:
    run_id: str
    run_dir: Path            # CWD исполнителя
    step: int                # шаг внутри сегмента цикла
    sequence: int            # позиция журнала: уникальна для всего прогона
    order: dict
    mode: str
    prompt: str
    allowed_paths: list[str]
    evidence: list[str]      # замечания предыдущей проверки
    runtime_dir: Path
```

Два правила контракта:

1. **`artifacts` в результате — это отчёт, а не заявка.** Цикл сдаёт только
   объявленные артефакты, которые реально существуют на диске
   (`work_order_submit_plan`). Исполнитель не может назвать путь, которого нет,
   или путь вне прогона.
2. **Адаптер обязан завершаться сам.** Жёсткий таймаут на шаг — часть контракта:
   CLI без настроенного провайдера умеет висеть вместо ошибки.

## 3. Состав пакета

| Модуль | Ответственность |
| :--- | :--- |
| `base.py` | протокол `Executor`, `RunContext`, `ExecutionResult`, `RuntimeFailure` |
| `submit.py` | `work_order_submit_plan/paths`: что именно разрешено сдавать |
| `prompt.py` | сборка промпта: карточка роли, стадия, pending-артефакты, шаблоны, правила |
| `loop.py` | `run_loop`: order → execute → проверка → submit → verify → gate |
| `guard.py` | отпечаток `state.json`, `blackbox.jsonl`, `blackbox.lock` и каталога прогонов |
| `usage.py` | `runtime/usage.jsonl`, суммы, проверка бюджета режима |
| `evidence.py` | `runtime/evidence/*.json`: факты для гейта и для человека |
| `fake.py` | детерминированный исполнитель на эталонных артефактах |
| `opencode.py` | `opencode run --format json ...` с таймаутом |
| `hermes.py` | `hermes -z ... --in ... --usage-file ...` с реальными токенами |
| `sandbox.py` | обёртка `bwrap`: read-only корень и управляющая плоскость, запись только в объявленные артефакты |
| `worktree.py` | параллельные задачи `s4_build`: seed-репозиторий, worktree на задачу, merge с проверкой хеша базы, откат и очистка |

## 4. Цикл `factory run`

```text
next_action ─┬─ complete ─────────────────────────────► 0
             ├─ blocked / wait ───────────────────────► 3
             ├─ gate, approver = human ───────────────► 2 (печать команды)
             ├─ gate, approver = роль ── verify ──────► gate_approve | gate_reject
             ├─ verify (задача) ── validate ──────────► task_accept | task_reject
             └─ produce / verify (стадия)
                    │
                    ├─ Fingerprint.capture(run_dir)
                    ├─ build_prompt
                    ├─ executor.execute
                    ├─ Fingerprint.capture → drift? ──► 3 (tampered)
                    ├─ usage.jsonl + budget ──────────► 3 (budget)
                    ├─ work_order_submit_plan → submit_work (по владельцам)
                    └─ следующая итерация
```

Коды выхода:

| Код | Значение |
| :--- | :--- |
| `0` | все стадии приняты, гейты закрыты |
| `2` | нужен человек: гейт с `approver: human` |
| `3` | эскалация: blocked, deadlock, tampered, budget, max_steps, падение исполнителя |

Если `verify` проходит, но `gate_approve` всё равно отказывает (например,
`plan.md` ссылается на роль, неактивную на `s4_build`), рантайм вызывает
`gate_reject` с текстом ошибки: стадия возвращается продюсеру, а не встаёт
намертво. Остановка `gate_failed` остаётся только для случая, когда отклонить
гейт тоже не удалось.

Человеческий гейт **никогда** не закрывается рантаймом. Даже при `--yolo`:
этот флаг передаётся только адаптеру Hermes и означает автоодобрение
инструментов агента, а не гейтов фабрики.

## 5. Что пришлось доработать в движке

### 5.1 Work order говорит, кто и что ещё не сдал

Главный пробел для режима `standard`: на мультиролевой стадии `roles` — это весь
список, `artifacts` — весь список, и рантайм вынужден угадывать, кто именно
должен действовать. Теперь каждый order несёт:

```json
"pending_artifacts": [
  {"id": "spec", "path": "artifacts/spec.md", "owner": "05-business-analyst",
   "errors": ["missing artifact: .../spec.md"]}
],
"next_role": "05-business-analyst"
```

`pending_artifacts` считается по каждому объявленному артефакту отдельно
(`artifacts.validate_artifact`), а не «стадия невалидна целиком». Для задач
`s4_build` скоуп сужается до одной задачи.

### 5.2 Пути для submit

`work_order_submit_plan(order, run_dir, task=None)` возвращает только объявленные
артефакты, которые существуют и непусты. Для задачи — только её `Allowed Files`
и `deliverable.md`: задача не может сдать весь `product/src/`, куда пишут другие
задачи.

### 5.3 Бюджет и стоимость шага

Журнал не хранит токены и цену. Рантайм пишет `runs/<id>/runtime/usage.jsonl`
(durable `step`, `loop_step`, стадия, роль, секунды, `tokens_total`,
`tokens_in`, `tokens_out`, `cache_read`, `api_calls`, модель, usd, exit code,
транскрипт) и после каждого шага сверяет сумму с бюджетом режима из
`pipeline.yaml`. `step` считается по всей длине журнала, а не по одному
вызову `factory run`: после человеческого гейта CLI запускается снова, и
прежний счётчик начинался с единицы.

Неизвестные числа остаются `null`: если адаптер не умеет отдавать токены,
проверка токенов пропускается, а не превращается в ноль. Бюджет `nano` —
2.5M токенов / 120 минут / $6; `standard` — 2.5M / 120 / $25.

#### Из чего состоит шаг

`total_tokens` CLI считает токены **каждого** API-вызова, включая повторное
чтение кешированного префикса. Поэтому один «шаг» фабрики — это не один
запрос: агент делает 2–7 вызовов, и системный промпт Hermes оплачивается
на каждом. Замеры 30 октября 2026 на реальном `s00_intake`:

| Прогон | Инструменты | API | input | cache read | output | **total** | сек |
| :--- | :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| baseline Hermes, пустой запрос | все | 1 | 22 089 | 0 | 77 | **22 166** | — |
| baseline `--safe-mode` | все | 1 | 9 | 22 080 | 49 | **22 138** | — |
| baseline `--ignore-user-config` | все | 1 | 9 | 22 080 | 50 | **22 139** | — |
| baseline `--ignore-rules` | все | 1 | 9 | 22 080 | 23 | **22 112** | — |
| baseline, пустой запрос | `file,terminal` | 1 | 5 730 | 0 | 18 | **5 748** | — |
| baseline, пустой запрос | `file` | 1 | 4 384 | 0 | 13 | **4 397** | — |
| baseline, дешёвая модель Qwen3.8-27B | `file` | 1 | 4 688 | 0 | 6 | **4 694** | — |
| фабричный шаг `s00_intake` | все | 3 | 26 901 | 49 984 | 2 323 | **79 208** | 49.5 |
| фабричный шаг `s00_intake` | `file,terminal` | 7 | 12 180 | 59 072 | 2 839 | **74 091** | 70.6 |
| фабричный шаг `s00_intake` | `file` | 2 | 7 850 | 6 208 | 1 702 | **15 760** | 24.9 |
| фабричный шаг `s00_intake`, Qwen3.8-27B | `file` | 6 | 13 376 | 49 856 | 3 495 | **66 727** | 35.8 |

Промпт фабрики в этих замерах — 5 387 символов (≈1.3k токенов); в более
раннем прогоне с полным набором инструментов — 7 692 символа. Разбор
79 208 токенов:

- системный промпт, описания инструментов и скиллов Hermes — ≈66k (≈84%):
  22 089 input-токенов на вызов × 3;
- фабричный промпт (`build_prompt`) — ≈5.7k (≈7%): 1.9k токенов × 3;
- ответ и reasoning — 2.3k (≈3%);
- результаты инструментов и прочее — ≈5k (≈6%).

То есть дорог не текст задания, а число вызовов, на каждом из которых
повторяется системная часть. `--safe-mode`, `--ignore-user-config` и
`--ignore-rules` в этом профиле не уменьшают контекст: кешированный префикс
остаётся тем же (22 080 токенов). Дешёвая модель сама по себе тоже не
уменьшает *токены*: Qwen сделал 6 вызовов вместо 2 и обошёлся в 66 727.

#### Что изменено

`HermesExecutor` по умолчанию использует `--executor-tools auto`:

- `file` для всех стадий, кроме `s4_build`: артефакты — Markdown/JSON, веб,
  браузер, делегирование и картиночные схемы не нужны;
- `file,terminal` для `s4_build`: исполнитель запускает проверочную команду
  продукта.

Это единственное изменение, которое сократило тот же шаг с 79 208 до 15 760
токенов (5.0×) без потери качества: `factory verify --stage s00_intake` — OK.
`--executor-tools all` возвращает полный набор для отладки.

#### Вывод по бюджету

- **`nano` 2.5M — измеренный бюджет для real Hermes.** Зелёный прогон
  `nano-todo` на `deepseek-ai/DeepSeek-V4.1-Flash-1017` (`--executor-tools
  auto`, `--reasoning high`, `bwrap`): 1 780 308 total / 336 980 billable,
  13 шагов, 10.5 минуты, все гейты. Три прогона одной конфигурации дали
  1.78–1.96M, поэтому 2.5M оставляет ~25 % запаса. Дешёвому исполнителю
  по-прежнему хватает 400k (документационная стадия — 15.7k), но дефолт
  больше не требует ручных флагов; `--budget-tokens` нужен, только если
  модель дороже измеренной.
- **`standard` 2.5M / 120 минут — по замеру.** Реальный `standard-mini` на
  Hermes: 15 шагов, 1 978 597 total / 363 237 billable, 11,2 минуты, все
  гейты; 2.5M оставляют ~26 % запаса. Прежние 1.5M были расчётом и
  остановили бы этот прогон на `s6_security` (1 553 552 после шага 12).
- **Цена в USD остаётся `null`.** `models.yaml` не содержит вендорских цен;
  `estimated_cost_usd` provider'а в этих прогонах — 0.0 при
  `cost_status: unknown`, поэтому USD-бюджет не проверяется, а не считается
  нулевым.

### 5.4 Evidence для гейта

`runtime/evidence/` содержит JSON на каждый шаг и на каждый человеческий стоп:
результат `verify`, хеш `state.json`, голову журнала и хеши сданных артефактов.
Гейт получает короткий список строк, а не весь журнал.

### 5.5 Вход стадии intake

Первый прогон через Hermes показал реальную дыру: на `s00_intake` модель
описала *свой* проект из памяти агента, потому что в прогоне не было ни одного
факта о продукте. Теперь `factory init --idea "..."` (и `factory run --idea`)
пишет `runs/<id>/idea.md`; промпт включает его как «единственный источник
истины о продукте», а tripwire считает файл защищённым. Без идеи интервью
бессмысленно: агент заполнит бриф тем, что помнит о машине.

### 5.6 Параллельные задачи `s4_build` в git worktree

`factory run --parallel-tasks N` собирает до N независимых задач одной волны
одновременно. Один worktree — одна задача:

- `runtime/worktrees/seed` — git-репозиторий с снимком продуктового дерева
  прогона (без `state.json`, журнала, usage, evidence и `runtime/`); коммит
  базы фиксируется до запуска;
- `runtime/worktrees/trees/<TASK-ID>` — detached worktree задачи; исполнитель
  работает только в нём, песочница открывает на запись только этот worktree
  и `runtime/agent/` управляющего прогона;
- `state.json`, `blackbox.jsonl`, `task_claim`, `submit_work` и `task_accept`
  пишет только главный поток после завершения всех воркеров: журнал остаётся
  single-writer;
- пересечение `Allowed Files` (включая каталог-префикс) отклоняется **до**
  создания worktree: `parallel tasks rejected: TASK-A and TASK-B both declare
  product/src/a.py`;
- слияние — копирование изменённых файлов с проверкой хеша базы. Если целевой
  файл изменился после базового коммита, это конфликт: скопированные файлы
  восстанавливаются, задача не сдаётся, worktree удаляется;
- задача, которая пишет вне своих `Allowed Files`, не сливается; упавшая
  задача не оставляет ни файлов, ни `claim`, ни `review` — только `pending`;
- после слияния `verify --stage s4_build` проходит по обычным правилам, а
  `task accept` идёт последовательно, как в обычном цикле.

Параллельный батч — один шаг цикла, но каждая задача пишет отдельную строку
`usage.jsonl` с `parallel: true`, своим `task_id`, токенами и секундами.
`--parallel-tasks 0` (по умолчанию) оставляет последовательный путь.

## 6. Безопасность

- **Песочница по умолчанию.** Для `hermes` и `opencode` команда всегда
  оборачивается в `bwrap`; `--no-sandbox` — явный отладочный флаг, который
  печатает предупреждение и оставляет только tripwire. `fake` внешних
  процессов не запускает и в песочнице не нуждается. Если `bwrap` не
  установлен, реальный исполнитель не стартует: `RuntimeFailure`, а не
  тихий запуск без границы.
- **Управляющая плоскость только для чтения.** Каталог прогона монтируется
  `--ro-bind`, а запись открывается точечно: объявленные ордером каталоги
  артефактов (`artifacts/`, `product/src/`, каталог задачи) и
  `runtime/agent/` для usage-файла Hermes. `state.json`, `blackbox.jsonl`,
  `blackbox.lock`, `idea.md`, `runtime/usage.jsonl` и `runtime/evidence/`
  остаются read-only. Поэтому `factory gate approve`, `factory submit` или
  `factory stage reset`, запущенные агентом, падают на `open()` с `EROFS`
  и не меняют ни состояние, ни журнал. Это проверено реальным вызовом CLI
  внутри песочницы: `gate approve` умирает на `blackbox.lock`, хеш
  `state.json` не меняется.
- **Корень проекта не монтируется на запись.** Root-артефакт (`s15:
  skills-lock.json`) открывается как отдельный файл. Каталог `factory/` и
  репозиторий целиком недоступны на запись: раньше `extra_read_write`
  включал весь `project_root`, и стадия карантина могла переписать движок.
  Путь, содержащий пакет `factory/`, отклоняется и в `--sandbox-rw`.
- **Параллельный worktree — отдельная граница.** Воркер получает
  `run_dir`-worktree, а не каталог прогона: песочница монтирует read-only сам
  worktree и открывает на запись только каталоги его `Allowed Files`,
  `deliverable` и `runtime/agent/` управляющего прогона. Соседний worktree,
  `state.json`, журнал и evidence для него read-only. Слияние выполняет
  главный процесс после остановки воркеров; воркер не вызывает `factory` и не
  пишет журнал.
- **Окружение очищается.** Адаптер удаляет из окружения потомка все
  `FACTORY_*` и `PYTHONPATH`: случайный вызов `factory` не получает ни корень,
  ни каталог прогонов, ни модель.
- **Tripwire — второй слой.** `guard.Fingerprint` хеширует `state.json`,
  `blackbox.jsonl`, `blackbox.lock`, `idea.md` и `runtime/usage.jsonl`, а
  также список файлов в каталоге прогонов. Подмена — остановка `tampered` с
  уликами. Без песочницы (`--no-sandbox`) это единственная защита, и она
  детектирует, а не предотвращает.
- **Что именно делает `bwrap`.** Read-only корень (`--ro-bind / /`), свои
  `/proc`, `/dev` и `/tmp`, отдельные PID/IPC/UTS-пространства,
  `--cap-drop ALL`, `--new-session`, `--die-with-parent`. Внешние каталоги,
  нужные CLI (кеш, сессии), добавляются через `--sandbox-rw PATH`. Путь,
  который содержит каталог прогона или пакет `factory/`, отклоняется, чтобы
  флаг не отменял границу. `--sandbox-rw ~/.hermes` даёт агенту запись в его
  собственный установленный CLI и в `cron/`, `hooks/`, `skills/` — это удобно,
  но это же и вектор самоподмены и автозапуска; передавайте минимальный набор
  (`cache`, `logs`, `state.db*`), а не весь home агента.
- **Остаточная граница.** Агент работает под тем же пользователем. `bwrap` —
  ядровая граница файловой системы, но не отдельный Unix-пользователь:
  доступные пользователю секреты и сеть остаются доступны. Настоящая
  изоляция «чужой пользователь или системный сервис» — следующий шаг, не
  `0.3.0`.
- **Бюджет не аутентифицирован.** `runtime/agent/usage-*.json` пишет сам CLI
  исполнителя; агент может занизить токены. Это учёт стоимости, а не граница
  безопасности: жёсткий таймаут шага остаётся, а внешний биллинг и сетевой
  лимит — отдельная задача.
- **Промпт** прямо запрещает трогать `state.json`, журнал, `.git` и `factory/`,
  писать вне прогона, оставлять `{{...}}` и пустые секции. Это дисциплина, а
  не контроль доступа; границу держит песочница.
- **Обратная связь по стадии.** Если все артефакты уже существуют, но
  `validate_stage` не проходит (REQ-паритет, покрытие плана, acceptance), промпт
  получает список этих ошибок и право перезаписать объявленные артефакты — без
  этого исполнитель видел «всё на месте» и не мог починить стадию.
- **Секреты** не передаются через промпт; адаптер наследует окружение только
  потому, что CLI провайдера читает свои ключи сам.

## 7. Тесты

`tests/test_runtime_loop.py`:

- полный `nano` на `FakeExecutor` до `complete`: 33 события, `verify --require-gate`
  без ошибок, `trace` 100%, `log verify` OK;
- human gate: остановка с кодом 2, гейт остаётся `pending`;
- «сломанный» артефакт: гейт не закрывается, цикл упирается в `max_steps`;
- запись в `state.json` → `tampered`;
- запись вне каталога прогона → `tampered`;
- исчерпание бюджета → `budget`;
- отчёт исполнителя не становится списком для submit;
- `work_order_submit_paths` учитывает только объявленные и существующие файлы.

`tests/test_runtime_adapters.py`: команда и разбор usage для OpenCode, реальные
токены и `failed: true` для Hermes, таймаут, отсутствующий бинарник, состав
команды `bwrap` и игнорирование `__pycache__` в фикстурах.

`tests/test_runtime_standard.py`:

- полный `standard` на `FakeExecutor` до `complete` (15 производительных
  шагов, 35 событий, `verify --require-gate` OK);
- мультиролевая стадия `s1_spec`: `05` и `06` получают отдельные шаги,
  `next_role` меняется, оба `ARTIFACT_SUBMIT` принадлежат своим ролям;
- `gate reject` на `s5_acceptance` возвращает задачи `s4_build` в `pending`,
  сбрасывает гейт `s4` и оставляет запись отказа `s5`.

`tests/test_runtime_worktrees.py`:

- две независимые задачи собираются в разных worktree одновременно (окна
  выполнения пересекаются), результаты сливаются, `verify --stage s4_build`
  проходит;
- пересечение `Allowed Files` отклоняется до создания worktree, state не
  меняется;
- падение одной задачи не оставляет ни файлов, ни `review` для неё;
- конфликт слияния (целевой файл изменился после базового коммита)
  откатывает скопированные файлы и не сдаёт задачу;
- `extra_read_write` воркера содержит только его worktree и
  `runtime/agent`, а не корень прогона.

`tests/test_runtime_trust_boundary.py` (реальный `bwrap`, не только argv):

- попытка дописать `state.json`, `blackbox.jsonl`, `blackbox.lock`, `idea.md`,
  `runtime/usage.jsonl` и `runtime/evidence/*` из песочницы завершается
  ошибкой, хеши не меняются;
- объявленный каталог `artifacts/` и `runtime/agent/` доступны на запись;
- корень прогона и каталог `runtime/` не монтируются на запись;
- `factory gate approve`, запущенный внутри песочницы, падает на
  `blackbox.lock` и не меняет `state.json`;
- root-артефакт открывается одним файлом, а не всем корнем проекта;
- `--sandbox-rw <project_root>` и путь, содержащий `factory/`, отклоняются;
- реальные исполнители по умолчанию идут в песочницу, `--no-sandbox` — только
  явно; окружение потомка не содержит `FACTORY_*` и `PYTHONPATH`.

## 8. Как запускать

```bash
# детерминированный прогон без модели и сети
factory run --run-id demo --executor fake --max-steps 60

# реальный исполнитель Hermes: песочница включена по умолчанию
factory run --run-id live --executor hermes --yolo --max-steps 60 --timeout 900 \
  --sandbox-rw ~/.hermes --sandbox-rw ~/.local/state --sandbox-rw ~/.cache

# стоимость: `auto` = file на документации, file+terminal на s4_build
factory run --run-id live --executor hermes --yolo --max-steps 1 \
  --executor-tools auto --executor-model <model-id>

# две независимые задачи s4_build параллельно, каждая в своём worktree
factory run --run-id live --executor fake --max-steps 60 --parallel-tasks 2

# отладка без границы: остаётся только tripwire, рантайм печатает предупреждение
factory run --run-id live --executor hermes --yolo --no-sandbox

# OpenCode (нужен выбранный провайдер в `opencode auth` / config)
factory run --run-id live --executor opencode --executor-model provider/model
```

Для изолированного прогона задайте `FACTORY_ROOT` (корень для root-артефактов)
и `FACTORY_RUNS_ROOT` (каталог прогонов). Каталог прогонов не должен лежать
внутри пути из `--sandbox-rw`: иначе `bwrap` отвергнет bind, потому что этот
путь содержал бы управляющую плоскость.

Прерванный на человеческом гейте прогон продолжается той же командой после
`factory gate approve`. Повторный `factory run` не пересоздаёт прогон и не
сбрасывает состояние.

| Адаптер | Статус | Что проверено |
| :--- | :--- | :--- |
| `fake` | работает | полный `nano` (33 события) и полный `standard` (15 шагов, 35 событий, `verify` OK); исполнитель пишет только артефакты своей роли, поэтому мультиролевые стадии проверяются, а не маскируются |
| `hermes` | работает | полный `nano-todo` на реальной модели: 13 шагов, 33 события, 1 780 308 total / 336 980 billable, 10.5 минуты, `verify` OK. Реальный `s00_intake` в песочнице: 79 208 токенов полным набором, 15 760 с `file`, 74 091 с `file,terminal` — разница в числе вызовов, а не в размере промпта (см. §5.3) |
| `opencode` | реализован, не проверен end-to-end | v2.0.29 установлен, но провайдер не выбран: `opencode run` висит и отдаёт `Transport: socket closed`. Нужен `opencode auth login` или провайдер в `~/.config/opencode/opencode.jsonc` |

Полный реальный `nano` прогнан 30.10.2026: 13 шагов, 1 780 308 total /
336 980 billable, 10.5 минуты, все гейты — `verify` OK. Прежняя оценка
0.4–0.8M оказалась заниженной в 3–4 раза: `total_tokens` считает каждый
API-вызов и повторно считает кешированный префикс, поэтому total и счёт
провайдера различаются в 5 раз. Бюджет `nano` поднят до 2.5M / 120 минут по
этому замеру; ручные флаги нужны, только если модель дороже измеренной.

Тот же замер для `standard-mini` (мультиролевая `s1_spec`, рамки
`constraints.md`): 15 шагов, 35 событий, 1 978 597 total / 363 237 billable,
11,2 минуты, все гейты. Бюджет `standard` поднят до 2.5M / 120 минут: прежние
1.5M остановили бы прогон на `s6_security` (1 553 552 после шага 12).

Второе наблюдение того же прогона: Hermes принёс в бриф знания из своей памяти
о машине пользователя. Поэтому `idea.md` обязателен, а промпт прямо запрещает
подменять его памятью. Изоляции контекста у CLI-агента нет; изоляция файловой
системы — `bwrap`, включённый по умолчанию.

## 10. Что дальше

- отдельный Unix-пользователь или системный сервис для исполнителя — следующая
  граница после `bwrap`; без неё агент остаётся в одном uid с фабрикой;
- подпись журнала (HMAC/Ed25519) — внешняя контрольная точка;
- `standard` на реальном исполнителе пройден (`standard-mini`, 15 шагов,
  35 событий, 1 978 597 total); гейты закрыты eval-харнессом как `human:eval`,
  поэтому живое ревью артефактов ролей `05`/`06`/`08` остаётся отдельным шагом;
- параллельные задачи `s4_build` реализованы (`--parallel-tasks`), но
  проверены на детерминированном исполнителе; реальный Hermes в worktree —
  после замера стоимости одного build-шага.
