# Рамки кейса `standard-mini`

## Требования

В `spec.md` и `spec-human.md` ровно три требования с этими идентификаторами:

- `REQ-001` — `start`: сотрудник запускает учёт времени по задаче; повторный
  `start` без `stop` завершается ошибкой, а не второй записью.
- `REQ-002` — `stop`: останавливает текущий интервал и сохраняет его в
  локальный JSON; `stop` без активного интервала — ошибка.
- `REQ-003` — `report`: печатает отчёт за неделю по сохранённым интервалам.

Хранение, формат JSON и обработка ошибок входят в текст этих трёх требований
как ограничения. Отдельные `REQ` для них не заводи: набор сверяется точно, и
лишнее требование ломает кейс.

## Задачи

`s4_build` состоит ровно из двух задач — `TASK-001` и `TASK-002`. Первая несёт
`start` и `stop` вместе с хранением, вторая — `report`, обработку ошибок и
тесты. Не дроби план по одной задаче на `REQ`.

## Стадия `s1_spec`

Стадию сдают две роли, каждая — только свои артефакты:

- `05-business-analyst` — `artifacts/spec.md`, `artifacts/spec-human.md`,
  `artifacts/traceability.json`;
- `06-system-analyst` — `artifacts/domain-model.md`,
  `artifacts/access-matrix.md`.

Одна роль не пишет файлы другой. Поле `tasks` каждого требования в
`traceability.json` ссылается только на `TASK-001` и `TASK-002`.

## Тесты продукта

В `product/tests/` не меньше трёх тестов, собираемых `pytest` (функции
`test_*`; классы `unittest.TestCase` тоже подходят). Запуск выполняется из
каталога прогона: `python -m pytest product/tests`.

## Пути

Все пути в артефактах и плане — относительно каталога прогона, без префикса
`runs/<run_id>/`.
